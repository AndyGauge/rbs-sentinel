# What is inline RBS?

Hand-writing and hand-maintaining a parallel `sig/` tree is where most RBS adoption efforts stall — it's a second codebase to keep in sync by hand. **Inline RBS** is the workaround the community converged on: write the type signature as a specially-formatted comment directly above the method it describes, and let a tool generate the real `.rbs` file from it.

```ruby
class UserSerializer
  #: (User) -> Hash[Symbol, untyped]
  def self.call(user)
    { id: user.id, name: user.name }
  end
end
```

The `#: (User) -> Hash[Symbol, untyped]` line is the annotation. It sits next to the code it types, gets reviewed in the same diff as the method, and moves with the method when it's refactored — none of which is true of a signature living in a separate file three directories away.

A generator (Sentinel, or [rbs-inline](https://github.com/soutaro/rbs-inline), the gem that popularized this convention) walks your source, finds these comments, and emits the matching `.rbs`:

```rbs
# Generated by Sentinel - Do not edit manually

class UserSerializer
  def self.call: (User) -> Hash[Symbol, untyped]
end
```

You never hand-edit the generated file — it's a build artifact, checked in so Steep and CI can read it without re-running the generator, but always treated as disposable.

## The annotation surface

Beyond plain method signatures, the same `#:` convention covers the shapes you actually need in a real codebase:

| What | Annotation |
|---|---|
| Instance method | `#: (String) -> void` above `def name` |
| Self/class method | `#: (String) -> Widget` above `def self.name` |
| `attr_reader`/`writer`/`accessor` | `#: String` above the `attr_*` call |
| Type alias | `# @rbs type user_id = String \| Integer` |
| Shared type import | `# @rbs import user_id` (resolves from `sig/shared/`) |

That last one — `# @rbs import` — is how you reuse a type across files without redefining it everywhere: Sentinel resolves it from `sig/shared/`, follows transitive references, and handles cycles. See the [feature comparison](./comparison.md) for the full annotation surface and where Sentinel and rbs-inline currently differ.

## No header required

rbs-inline requires an opt-in header comment (`# rbs_inline: enabled`) at the top of every file it should process — useful for a gradual rollout, but one more thing to remember to add, and easy to silently skip a file. Sentinel has no such header: any file inside a watched folder (configured in `.sentinel.toml`) is scanned. That matters most when you're retrofitting types onto a large existing codebase, or a Rails engine, where you don't want to touch every file's top line just to opt it in.
